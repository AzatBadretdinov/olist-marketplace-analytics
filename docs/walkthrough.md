# Как разбирать проект

1. Открой README и business_report: сформулируй бизнес-вопрос и три результата своими словами.
2. В data_understand.py разбери цикл, проверки ключей и смысл одной строки каждой таблицы.
3. В 05_analytics_views.sql найди item_totals и payment_totals. Объясни, почему сырой JOIN дал бы завышенные суммы.
4. Разбери ROW_NUMBER для отзывов и NULL is_late при неизвестной доставке.
5. Выполни запросы 06_business_analysis.sql по одному. Объясни числитель и знаменатель каждой доли.
6. В ноутбуке анализа проверь сравнение января–июля двух лет и причины исключения краёв.
7. В статистическом ноутбуке объясни H0/H1, разность долей, доверительный интервал и ограничения причинности.
8. В Excel поменяй штат и период. Проследи Dashboard -> Monthly -> Data.
9. В scripts/build_analysis.py изучи verify_sources: почему сверка по каждому заказу сильнее сверки общего итога.
10. Повтори запуск из чистой папки по README.

## Вопросы для собеседования

- Почему GMV нельзя назвать выручкой Olist?
- Почему используешь customer_unique_id, а не customer_id для уникальных покупателей?
- Почему order_id не обязан быть уникален в payments и reviews?
- Что изменится, если сравнить timestamps с обещанным полуночным временем вместо календарных дат?
- Как учитываются восемь delivered-заказов без фактической даты?
- Почему большое p-value и маленькое p-value не отвечают на вопрос о причинности?
- Какие дополнительные данные нужны для оценки экономического эффекта?
- Как проверить, что фильтры Excel не усредняют уже готовые проценты?

## Формулировка для резюме после самостоятельного разбора

Выполнил end-to-end анализ исторических данных маркетплейса Olist: PostgreSQL-витрины,
контроль качества и сверка с CSV, Python EDA, проверка связи доставки с оценками,
Excel-отчёт с фильтрами и обоснованные рекомендации.

Числа добавляй из отчёта. Не приписывай проекту реальное улучшение бизнеса или проведённый A/B-тест.
Реализация этой версии подготовлена с помощью ИИ; важно уметь самостоятельно объяснить и воспроизвести решения.
